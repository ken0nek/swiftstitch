# nitrogen-swift-input

SwiftPM CLI. Reads `Hybrid<Name>.swift` source files and emits the
nitrogen-compatible spec: `<Name>.nitro.ts` + `<Name>.ir.json`.

This README is the executive summary. Exact CLI semantics, architecture,
the IR JSON contract, the error catalog, and the test map live in
[`RUNBOOK.md`](RUNBOOK.md).

## When to use this

You want to author a HybridObject's interface in **standard Swift** instead
of writing a `.nitro.ts` interface by hand. Detection is by class-naming
convention (`Hybrid<Name>`) — no attribute, no macro, no compile
dependency: your project compiles whether or not this CLI has run.

- If you already run JavaScriptKit's BridgeJS prepass, prefer
  `nitrogen-swift-bridgejs` (see the root README's package table).
- The IR JSON output additionally enables the future no-`.nitro.ts` path
  (`nitrogen-swift-spec-input`).

## Toolchain

Swift **5.10+** on the codegen host (macOS 13+); `swift-syntax` pinned
`from: 510.0.0`.

## Build

```sh
swift build --package-path packages/nitrogen-swift-input
# binary: packages/nitrogen-swift-input/.build/debug/nitrogen-swift-input
```

## Authoring loop

```
① nitrogen-swift-input init Counter      # scaffolds swift/HybridCounter.swift + chains a first emit
② add autolinking.Counter to nitro.json  # init does not do this yet
③ edit swift/HybridCounter.swift         # public methods = the spec surface;
                                         # the same file ships as the iOS impl
④ nitrogen-swift-input emit              # zero-flag re-run after each spec edit
⑤ bun nitrogen specs && pod install      # stock nitro from here on
```

Consumers of your published module never run any of this — the generated
outputs ship with the package (`bun add` + `pod install` is their whole
story).

## Scaffolding a new HybridObject

`init <Name>` accepts the spec name (`Counter`) or the class name
(`HybridCounter`) — the prefix is stripped either way. It writes:

```swift
// HybridCounter.swift — generated by `nitrogen-swift-input init Counter`.
//
// This file is BOTH:
//   1. The spec source — parsed by `nitrogen-swift-input` (SwiftSyntax, no
//      typecheck) to emit `Counter.nitro.ts` + `Counter.ir.json`.
//   2. The implementation — compiled into the Pod that ships in the RN app.
//
// The `: HybridCounterSpec` inheritance and `import NitroModules` only resolve
// after `bun nitrogen` produces
// `nitrogen/generated/ios/swift/HybridCounterSpec.swift` and `pod install`
// brings in NitroModules. The `#if canImport(NitroModules)` wrap lets this
// file parse cleanly before that first codegen run.
//
// Standard Swift from here on — add public methods, run codegen, ship.

#if canImport(NitroModules)
import NitroModules

public final class HybridCounter: HybridCounterSpec {
    public override init() { super.init() }

    // Add public methods here. Supported parameter / return types: Bool,
    // Double, Float, Int64, UInt64, Void. Example:
    //
    //   public func add(a: Double, b: Double) throws -> Double { a + b }
}
#endif
```

`--out <dir>` changes the Swift destination (default `swift/`), `--force`
overwrites, and the chained first emit defaults to
`--ios swift --android kotlin` (override with either flag).

## What the parser reads

- Any class named `Hybrid<Name>` (prefix plus at least one character). The
  TS interface name is the class name minus the prefix (`HybridMath` →
  `Math`).
- Only `public` methods. `init` and non-public members are ignored by
  design.
- Multiple `Hybrid*` classes in one file all surface (outputs are named
  after the first — prefer one class per file).
- The `#if canImport(NitroModules)` wrap is fully supported: parsing is
  SwiftSyntax-only, never typechecks, and walks inactive `#if` branches.

### Type scope

| Swift | TS | Notes |
|---|---|---|
| `Bool` | `boolean` | |
| `Double`, `Float` | `number` | `Float` folds to nitrogen's NumberType (= double) |
| `Int64`, `UInt64` | `Int64`, `UInt64` | typed aliases imported from `react-native-nitro-modules` |
| `Void` / `()` / implicit | `void` | |

`throws` is captured in the IR (`isThrowing`) but doesn't surface in TS —
nitrogen wraps every generated Swift method in `throws` regardless.

Out-of-scope **types** (`String`, arrays, optionals, plain `Int`/`UInt`
widths, structs/enums/closures/generics used as types) are rejected with a
`file:line:col` diagnostic. **Silently mishandled today** (no diagnostic):
public properties are dropped, `static`/`class` funcs are extracted as
instance methods, `async` is treated as sync — see
[`RUNBOOK.md`](RUNBOOK.md) § Known gaps.

## Outputs

| Output | What it is |
|---|---|
| `specs/<Name>.nitro.ts` | The TS spec stock `bun nitrogen` consumes. |
| `specs/<Name>.ir.json` | Schema-v1 IR — keeps `isThrowing` + parameter labels the TS format throws away (no source locations). For the future spec-input path; useful for debugging. |

Both are emitted by default; naming `--out <dir>` or `--out-json <dir>`
alone opts into a TS-only / JSON-only run. Example emitted spec:

```ts
import type { HybridObject } from 'react-native-nitro-modules'

export interface Math extends HybridObject<{ ios: 'swift' }> {
  add(a: number, b: number): number
}
```

End-to-end walkthrough (Swift source → generated C++/Swift bridge):
[`example/nitrogen-swift-input/`](../../example/nitrogen-swift-input/).

## CLI

```
nitrogen-swift-input init <Name> [--out <dir>] [--ios <lang>] [--android <lang>] [--force]
nitrogen-swift-input emit [--input <swift-file> ...] [--out <dir>] [--out-json <dir>]
                          [--ios <lang>] [--android <lang>]
```

Zero-flag defaults: inputs glob `swift/Hybrid*.swift`; outputs land in
`specs/`; per-spec platforms come from `nitro.json`
(`autolinking.<Spec>.{ios,android}.language`) — CLI platform flags, if
present, override `nitro.json` wholesale. Full resolution rules, exit
codes, and the error catalog: [`RUNBOOK.md`](RUNBOOK.md) § CLI reference.
